# Compasso Migration Implementation Plan

> **For agentic workers:** Execute tasks in this session, with a verification checkpoint after each task. Steps use checkbox (`- [ ]`) syntax for tracking. The user has already authorized implementation; do not request a second execution approval. Repository commands and task authorization take precedence over generic workflow examples.

**Goal:** Migrate the five client web apps to shared identity, family authorization, Compasso subscription and AI wallet, delivering the account central and retiring superseded implementations without losing data or existing contractual rights.

**Architecture:** Modular packages in the existing monorepo, PostgreSQL schemas with explicit relations and transactional authorization, separately deployed Next.js apps. Shared service contracts execute in each server; the account UI is not a mandatory HTTP hop for domain operations. Keep Edi licensing and children's device sessions isolated.

**Tech Stack:** Node 24.15.0, pnpm 9.15.0, TypeScript, Next.js, React, Drizzle/PostgreSQL, Better Auth 1.7.10, Stripe 22.1.0, Redis, Railway, Vitest and Playwright at the locked versions.

**Spec:** [implementation contract](../../propostas/assinatura-web-2026-11-09/implementacao.md) and [approved visual direction](../../propostas/assinatura-web-2026-11-09/proposta.html).

## Global Constraints

- R$ 49,90/month or R$ 499/year, two adults, four dependents, explicit 14-day trial without a card.
- Approved AI policy: 200 monthly credits, 20 trial credits, purchased credits without expiry; packs 100/R$14.90, 300/R$39.90, 1000/R$99.90. Preserve old balances' validity and purchasing power.
- No app-to-app imports, no package-to-app imports, no new provider, no dependency upgrades.
- Generated schema migrations are not edited; data backfills use custom migrations generated through the repository script.
- Tests use isolated PostgreSQL and synthetic accounts; no production content or secrets in artifacts.
- Preserve `.claude/settings.local.json`; no automatic commit/push/release outside the task's agreed gates.
- Do not finish with duplicate identity or wallet write paths. Preserve historical migrations and financial evidence.

## Task 2: People, groups and scoped authorization

**Files:** new `packages/db/src/schema/family.ts`; schema index/config; new `packages/family/{package.json,tsconfig.json,src/index.ts,src/types.ts,src/errors.ts,src/people.ts,src/groups.ts,src/access.ts,src/invitations.ts,src/links.ts}` and focused tests/integration config.

**Interfaces:** `createFamilyService({ db, now?, audit? })`; methods `createGroup(actorId, name)`, `createPerson(actorId, input)`, `listPeople(actorId, groupId)`, `updatePerson(actorId, input)`, `grantAccess(actorId, input)`, `revokeAccess(actorId, input)`, `assertPersonAccess(actorId, target)`, `linkProfile(actorId, input)`. Target includes group ID, person ID, app and action. Actor always comes from authenticated server context.

- [ ] Define independent `groups`, `members`, `people`, `group_people`, `app_profiles`, `access_grants`, `invitations` and content-free audit rows. Use composite FKs for context integrity, unique active links and row locking for mutations.
- [ ] Implement authorization without implicit payer access. A group admin manages membership; another adult's private profile still requires an explicit grant. Reject cross-group IDs, self-escalation, revoked membership and archived people.
- [ ] Implement create/update/archive, invitation accept/revoke and profile association in transactions; verify existing target ownership before linking. Do not merge by name.
- [ ] Generate schema migration and run real integration tests: concurrent capacity reservations cannot exceed the approved limit, grants cannot point outside their group, a revoked member is denied on the next authoritative check, and replaying an invitation does not create another membership.

```ts
await expect(family.assertPersonAccess(otherAdult, {
  groupId, personId, app: "agenda-da-turma", action: "read",
})).rejects.toMatchObject({ code: "ACCESS_DENIED" });
```

## Task 3: Deterministic backfill and app identity integration

**Files:** generated/custom `packages/db/src/migrations/*`; `agenda.ts`, `agenda-family.ts`, `bora-treinar.ts`, `dia-de-estrela.ts`, `missao-saber.ts`; all profile repositories/actions and selectors found in the consumer inventory; new `packages/family/src/migration.ts` and migration integration tests.

**Interfaces:** each local profile references an authoritative person and group while retaining its original profile ID. `linkProfile` receives the observed source binding/version and explicit destination person; conflicting or unauthorized bindings fail atomically.

- [ ] Backfill one group per existing ownership context and one person per original profile; preserve original grants and IDs. Store provenance for reconciliation, never infer equality from name.
- [ ] Migrate profile readers to joins with common identity; migrate create/update paths to family transactions. Add selection of existing people to each first-use flow.
- [ ] Provide explicit association in the account central. One person may have distinct contextual histories; reject merging two conflicting profiles in the same context.
- [ ] Exercise before/after fixtures for all four apps, including existing invitations and paired devices. Remove duplicated name/avatar fields only after every reader/writer is converted and backfill constraints pass.

**Interfaces:** wallet is identified independently of consuming app; reserve includes authorized wallet, actor, app, operation and runId. `getCollectionAccess` resolves paid contract or explicit trial and covered people. Existing contracts continue through this single engine.

- [ ] Separate collection ownership from consuming app in the service and schema. Add relational wallets and coverage; use a wallet transaction lock for reserves, settlement, grants, expiry and migration.
- [ ] Normalize cost per operation from current pricing and bounded workloads; present monthly grant and topups before provisioning chargeable amounts.

- [ ] Test two apps competing for one remaining credit, repeat settlement, interrupted execution, renewal, refund, cancellation, annual cycles and old contractual entitlements. Re-run Edi payment/license integration.
